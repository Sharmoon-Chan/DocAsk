# Java 高频面试学习笔记：JVM 与垃圾回收

基于小林coding公开资料学习整理，非官方原文、非官方知识库。本文归纳 JVM 复习中的常见重点；“高频”表示复习优先级，不代表统计排名。整理日期：2026-11-11。规范概念与 HotSpot 的版本实现分别说明。

## Q01 JVM 运行时数据区与 Java 内存模型 JMM 是一回事吗？

JVM 运行时数据区回答数据保存在哪里：堆保存对象和数组，方法区保存类级信息；每个线程有自己的虚拟机栈、本地方法栈和程序计数器，堆与方法区在线程间共享。JMM 回答多个线程如何正确观察共享数据，重点是可见性、原子性、有序性和 happens-before。JMM 的“主内存、工作内存”是抽象描述，不能直接对应堆与栈。方法区是虚拟机规范概念，JDK 8 及以后 HotSpot 用元空间保存类元数据，不能因此说方法区被取消。直接内存位于堆外，但不属于规范定义的这五类运行时数据区。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。

## Q02 堆和栈分别保存什么，-Xmx 与 -Xss 调整的是哪里？

方法调用会在当前线程栈中形成栈帧，保存局部变量、操作数栈和返回信息；局部变量可以保存对象引用，被引用的普通对象和数组通常在堆中。`-Xms` 与 `-Xmx` 控制堆初始容量和最大容量，`-Xss` 控制线程栈大小。深递归可能产生 StackOverflowError，大数组无法分配则可能产生堆 OutOfMemoryError，两者不能混为一谈。把引用设为 null 只可能减少一条引用链，不会立即释放对象。增加线程栈有时可容纳更深调用，却也提高大量线程的本地内存需求，应先检查递归终止条件和线程数量。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。

## Q03 元空间在堆里吗，为什么还会出现 Metaspace OOM？

JDK 8 及以后的 HotSpot 将类元数据放在使用本地内存的元空间，元空间不属于 Java 堆。改用本地内存不代表容量无限：它受进程可用内存及 `-XX:MaxMetaspaceSize` 等限制，仍可能报 `OutOfMemoryError: Metaspace`。`MetaspaceSize` 主要是触发相关 GC 的初始阈值，不是固定预分配容量。大量生成代理类、反复创建类加载器却无法卸载，都是排查方向；应沿引用链找出谁仍持有类加载器。还要区分 JIT 的 Code Cache、元空间和堆中的字符串对象，不能把所有“类相关数据”都算进元空间。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。

## Q04 类加载有哪些阶段，加载就一定执行静态代码块吗？

常用划分是加载、连接、初始化；连接再分验证、准备和解析。加载把字节码转为运行时类信息，验证检查合法性，准备为静态字段建立初始状态，解析处理符号引用，初始化执行静态赋值与静态代码块形成的类初始化逻辑。加载并不等于初始化，`User.class`、创建 `User[]` 或通常的 `loadClass()` 不会因为这些动作就执行 User 的静态代码块。new、调用静态方法等主动使用才按规则触发初始化。准备阶段对带 ConstantValue 的字段有特殊处理，不能把所有 static final 字段都当成编译期常量；类初始化也不同于实例构造方法。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。

## Q05 双亲委派是什么，能保证同名类在整个 JVM 里只有一份吗？

常规类加载器在需要加载类时，先检查是否已加载，再优先委派给父加载器；父层无法完成时，当前加载器再尝试自己的查找逻辑。这有助于复用上层定义的类，并避免应用路径中的同名类型轻易覆盖核心类。它是一种常用策略，不是所有自定义加载器都必须遵守的规则。JVM 中类型身份还包括定义它的类加载器，因此两个加载器分别定义同一全限定名，仍可能得到不同类型并出现转换失败。JDK 8 常见的扩展类加载器在 JDK 9 起被平台类加载器替代；回答时应区分版本，不把 rt.jar 和扩展目录机制套到现代 JDK。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。

## Q06 GC 怎样判断对象可回收，循环引用会阻止回收吗？

常见 Java 垃圾收集器通过可达性分析判断对象存活，从 GC Roots 出发沿引用关系访问对象。根的常见来源包括线程栈中的引用、存活类的静态字段、JNI 引用以及 JVM 需要保持的对象。两个对象相互引用，但整体已无法从根到达，仍可能被回收，因此循环引用并不是可达性分析的障碍。对象不可达也不代表马上释放，要等相应回收过程。强、软、弱、虚引用会影响对象的可达性与通知语义；弱引用不保证对象一直存活。文件、数据库连接等外部资源应及时显式关闭，不能把 GC 当作业务资源释放时机的保证。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。

## Q07 标记清除、复制和标记整理各有什么取舍？

标记清除先识别存活对象，再回收不可达对象，避免大规模移动，但可能留下内存碎片。复制把存活对象迁移到另一片空间，之后整体回收原区域，分配更规整，代价是复制开销和预留空间。标记整理在确定存活对象后移动它们以压紧空间，减少碎片，但需要协调引用更新。具体收集器可能按区域和阶段组合这些手段，不能只凭一个算法名称推断停顿或吞吐。分代设计利用许多对象很快死亡的现象，让年轻区域回收与长期存活区域区别处理；不同收集器的物理布局和回收范围不同，不能认为所有 JVM 都固定采用同一套比例与算法。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。

## Q08 G1 的 Region、Mixed GC 与停顿目标应该怎么理解？

G1 将堆拆成多个 Region，保留年轻代和老年代的逻辑划分，但它们不必各占一整块连续地址。Young GC 回收年轻区域，Mixed GC 同时选择部分老年代区域，后者并不等于整个堆的 Full GC。并发标记可以与应用线程共同推进，但部分阶段和对象转移仍需要 Stop-The-World，所以 G1 不是“完全无停顿”。`-XX:MaxGCPauseMillis` 是调度时参考的目标，不是每次停顿的硬保证。超过单个 Region 一半的大对象按 Humongous 方式分配，可能引发连续区域不足与空间浪费；频繁大对象分配应先考虑分批和流式处理，再根据日志调整参数。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。

## Q09 内存泄漏和 OOM 有何区别，应该怎样开始排查？

内存泄漏指业务不再需要的对象仍被长期引用，GC 无法回收；OOM 指申请内存失败，可能来自泄漏，也可能来自合理数据量超过容量、一次性大分配或本地资源不足。先读异常类型，区分 Java heap space、Metaspace、direct buffer 和无法创建本地线程，再关联请求量、分配速率、GC 后占用和线程数量。`jcmd <pid> GC.heap_info`、JFR 和 GC 日志可帮助观察；必要时保存堆快照，用支配树及到 GC Roots 的路径查持有者。堆快照可能带来停顿和磁盘消耗，应结合运行条件操作，不能一出现 OOM 就只调大 -Xmx。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。

## Q10 TLAB 与逃逸分析是什么，对象一定在栈上或堆上实际分配吗？

TLAB 是线程本地分配缓冲区，常见 HotSpot 收集器可在堆里给线程划出一小段分配空间，减少创建对象时争抢共享分配指针。它位于堆，不是线程栈，分配后的对象也可以被其他线程引用，仍由 GC 管理。逃逸分析则研究对象是否会离开当前方法或线程；在满足优化条件时，JIT 可能做标量替换、消除分配或不必要的锁。没有逃逸不等于必然优化成功，也不能简单说“局部对象一定在栈上”。规范层面对象和数组由堆承载，实际执行可能连完整对象都没有构造，答题时应把通常布局与编译优化分开。

来源：[小林coding：Java虚拟机面试题](https://xiaolincoding.com/interview/jvm.html)。
