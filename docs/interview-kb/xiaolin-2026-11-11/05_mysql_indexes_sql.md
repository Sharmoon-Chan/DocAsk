# Java 面试知识库：MySQL 索引与 SQL

整理日期：2026-11-11。本文依据小林 coding 的公开文章编写，是面向面试复习的原创学习总结，非官方原文或逐句转载。“高频”表示备考优先级，不代表统计排名。除特别说明外，以 MySQL 8.0、InnoDB 为讨论前提；示例表名和数据仅用于解释原理。

## Q01 一条 SELECT 语句在 MySQL 中怎样执行？

查询一般经过连接与身份校验、语法解析、预处理、优化和执行。解析器检查语法并构造语法树，预处理解析表和字段，优化器比较访问路径成本，执行器调用存储引擎读取记录并返回结果。索引查找、数据页访问等由存储引擎完成，不能把整条查询都归到优化器。

MySQL 8.0 已移除 Server 层的 Query Cache，但 InnoDB 的 Buffer Pool 仍然缓存数据页和索引页，命中后无需每次访问磁盘。例如主键点查慢，除了检查执行计划，还要区分锁等待、连接排队、磁盘读取和结果传输；看到一个慢查询，不能直接认定是“没有索引”。

## Q02 为什么 InnoDB 常用 B+ 树，而不是哈希表或二叉树？

B+ 树的一个页能容纳较多索引项，分支多、树高相对低，适合按页读取的存储系统。内部节点主要保存导航用的键和指针，叶子层保存索引记录并按键有序连接，因此既能做等值定位，也适合范围扫描和按索引顺序读取。二叉树的分支少，数据量大时路径通常更长。

哈希结构擅长等值查找，却不能直接提供有序范围扫描，例如 `id BETWEEN 100 AND 200`。树高也不等于一次查询必然发生同样次数的磁盘读取：上层页可能已在 Buffer Pool 中；主键宽度、页大小、记录大小和填充程度都会影响树高，不能背成“千万行固定三次磁盘 I/O”。

参考：[索引常见面试题](https://xiaolincoding.com/mysql/index/index_interview.html)

## Q03 聚簇索引、二级索引、回表分别是什么？

InnoDB 把行记录组织在聚簇索引的叶子页中，通常使用主键作为聚簇键；二级索引的叶子记录包含二级索引列和对应主键。通过二级索引找到主键后，再去聚簇索引获取缺少的列，这一步叫回表。例如 `name` 有索引时，查询某人的其他未索引字段通常需要回表。

若只查询二级索引已经包含的列，则有机会形成覆盖索引，减少回表。未显式声明主键时，引擎会寻找合适的非空唯一索引，否则生成内部行标识。主键过长会放大所有二级索引；随机主键可能增加页分裂，但是否换成递增键还要结合写入分布、唯一性和业务需求判断。

参考：[索引常见面试题](https://xiaolincoding.com/mysql/index/index_interview.html)

## Q04 联合索引的最左前缀原则是什么，遇到范围条件就全部失效吗？

联合索引 `(a,b,c)` 按列的先后次序排序，先按第一列，再在第一列相等时比较后面的列。`a=1 AND b=2` 可构造较窄的查找范围，SQL 中条件的书写顺序不决定索引顺序；只按后缀列筛选，通常无法像完整前缀一样直接定位。

范围条件主要影响后续列继续缩小扫描区间的能力，不等于整棵索引失效。后续列仍可能用于索引下推、覆盖查询；某些包含边界的条件还能参与构造边界。优化器也可能选择索引全扫描或特定条件下的跳跃扫描。分析时要区分“用于定位”“用于过滤”“仅用于覆盖”，不能只看查询里有没有范围符号。

## Q05 覆盖索引和索引下推 ICP 有什么区别？

覆盖索引表示查询需要的列可以从某个索引取得，通常不必为了获取其他列而回表。索引下推则是把可仅凭索引列判断的部分条件交给存储引擎，先过滤候选索引记录，再回表读取剩余列。前者减少取整行的必要性，后者减少需要取整行的次数。

例如有 `(name,age)` 索引，按姓名前缀查找并筛年龄，同时还需要住址，年龄条件可通过 ICP 提前过滤，但住址仍可能要回表。执行计划的 `Using index` 和 `Using index condition` 含义不同。覆盖查询在某些 MVCC 可见性检查情形仍可能访问聚簇记录，因此“覆盖索引绝不访问主键页”不是无条件保证。

参考：[索引失效有哪些？](https://xiaolincoding.com/mysql/index/index_lose.html)、[索引常见面试题](https://xiaolincoding.com/mysql/index/index_interview.html)

## Q06 对索引列使用函数、计算或隐式类型转换有什么风险？

普通索引按列的原值排序，对列做函数或运算后，优化器通常不能直接把条件转换为该索引的有效查找范围。例如 `YEAR(created_at)=2026` 可考虑改为时间区间，`id+1=10` 可改为 `id=9`，但改写必须保持空值、时区和溢出等语义一致。

字符串列与数字比较时，可能需要逐行转换索引列；手机号等标识符应按字段类型绑定参数，避免前导零和转换问题。函数索引或匹配表达式的生成列索引可支持特定函数条件，所以不能断言“用了函数就绝对不能走任何索引”。最终结合字段类型、排序规则、实际参数和执行计划判断，不能只凭 SQL 外观下结论。

参考：[索引失效有哪些？](https://xiaolincoding.com/mysql/index/index_lose.html)

## Q07 LIKE、OR、低区分度条件是不是一定导致索引失效？

不能一概而论。`name LIKE '张%'` 有固定前缀，通常能形成范围；`LIKE '%张%'` 缺少左边界，通常不能做同样的范围定位，但仍可能使用覆盖索引扫描。`OR` 一侧没有可用访问路径时常倾向全表扫描，两侧均有合适索引时也可能采用 Index Merge。

低区分度列不是绝对不能建索引：某个少见状态可能很有选择性，联合其他条件也可能有效。若查询返回大部分记录，优化器即使知道有索引，也可能认为连续扫描比大量回表更便宜。排查时应同时检查数据分布、统计信息与结果集大小；“没有选择索引”和“无法形成索引范围”是不同原因。

## Q08 怎样用 EXPLAIN 定位慢 SQL？

先确定慢查询的实际参数和数据量，再用 `EXPLAIN` 查看连接顺序、访问类型、候选索引与实际索引，以及预估扫描行数和过滤比例。`key` 说明选了哪个索引，`key_len` 辅助判断用于查找的索引部分，不能仅凭“用了索引”就宣布优化完成。

还要看排序、临时表和回表成本；`Using filesort` 表示需要额外排序，并不必然已写磁盘。MySQL 8.0 支持的 `EXPLAIN ANALYZE` 会真实执行所分析的查询，可比较实际行数、循环次数和耗时，但线上大查询需要控制成本。优化后应在相近负载和参数分布下复测，关注扫描量和尾延迟，避免拿缓存冷热差异当成收益。

## Q09 为什么深分页慢，游标分页和延迟关联各解决什么？

`LIMIT 100000,20` 通常要先找到满足条件的前十万零二十条，再丢弃前十万条；如果过程中还大量回表，成本会更高。仅把返回数量设为二十，并不意味着引擎只处理二十条记录。延迟关联先从较窄的覆盖索引取得目标主键，再取完整行，可以减少无用回表，但没有消除偏移扫描。

连续翻页可记录上一页的排序键，用 `WHERE id>:lastId ORDER BY id LIMIT 20` 做游标分页。按时间排序时要增加唯一键作为并列值的判定依据，并配套联合索引。游标分页不适合任意跳页，数据并发修改也可能影响跨页结果；导出是否需要固定快照，应由业务一致性要求决定。

## Q10 COUNT(*)、COUNT(1)、COUNT(列) 有什么区别？

`COUNT(*)` 统计符合条件的行数，`COUNT(1)` 的常量永不为空，通常采用相同优化，不能说星号会读取全部列。`COUNT(col)` 只统计该表达式非空的行，如果列允许为空，结果本来就可能不同，不能为了所谓性能直接互换。

InnoDB 需要按照当前事务可见性统计，不能用一个全局行数同时回答所有快照，因此大表精确计数仍有扫描成本。可用较窄索引减少读取量，但过滤条件和执行计划也会影响选择。需要估算时可利用统计信息并说明不精确；使用独立计数表时，要把增减与业务写入的事务、重试幂等及修复机制一起设计，不能把缓存计数天然当作强一致真值。
