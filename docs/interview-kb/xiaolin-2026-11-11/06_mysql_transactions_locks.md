# Java 面试知识库：MySQL 事务、MVCC 与锁

整理日期：2026-11-11。本文依据小林 coding 的公开文章编写，是原创学习总结，非官方原文。“高频”表示备考优先级，没有统计排名含义。主要讨论 MySQL 8.0 的 InnoDB；隔离级别、索引、访问方式和具体版本会影响锁行为，示例不替代实际执行计划与锁信息。

## Q01 事务的 ACID 分别是什么，由什么机制支持？

原子性要求事务整体提交或回滚；一致性要求业务约束在事务前后成立；隔离性约束并发操作互相可见和干扰的方式；持久性要求成功提交的修改在约定故障模型下可以恢复。它们不是四个孤立开关，数据库也不会自动理解“转账总额守恒”等所有业务规则。

InnoDB 用 undo 支持撤销修改，用 redo 和刷盘策略支持崩溃恢复，用锁与 MVCC 实现不同隔离语义。一致性还依赖正确事务边界、唯一约束及应用校验。数据库事务不能自动回滚已经发送的邮件或远端接口调用；此类跨系统副作用需要幂等、可靠事件或补偿设计，不能把加上 `BEGIN` 当成跨服务原子性的证明。

## Q02 四种隔离级别和脏读、不可重复读、幻读如何对应？

脏读是读到其他事务未提交的数据；不可重复读通常指同一事务再次读取某行时值已变化；幻读关注相同谓词匹配的记录集合变化。读未提交允许脏读，读提交避免脏读，可重复读提供更稳定的一致性读，串行化要求结果等价于某种串行执行。

SQL 标准描述的是隔离语义，具体数据库实现不完全相同。InnoDB 默认可重复读，普通一致性读依靠 MVCC，范围锁定读则可借助间隙锁和临键锁限制插入。不能把“标准允许幻读”直接推成所有重复查询必然幻读，也不能说串行化让全库所有事务都排成一个队列；不冲突的访问仍可能并发，代价取决于实际冲突范围。

## Q03 MVCC 和 Read View 如何判断一个版本是否可见？

MVCC 结合记录的事务标识、undo 版本链和 Read View，让一致性读寻找对当前快照可见的版本，减少普通读与写之间的阻塞。它不是在事务开始时复制整张表；旧版本可以通过 undo 中的撤销信息重建。

Read View 保存创建者、活跃读写事务集合和事务编号边界。自己的修改通常可见；早于低边界的已提交版本可见，达到高边界的新版本不可见；落在中间则检查生成者在创建快照时是否仍活跃。不可见就沿版本链查找。这里判断的是快照建立时的状态，不是查询瞬间对方是否已经提交。长事务持续持有旧视图，会延迟历史版本清理并增加空间和查询成本。

参考：[事务隔离级别是怎么实现的？](https://xiaolincoding.com/mysql/transaction/mvcc.html)

## Q04 读提交 RC 和可重复读 RR 的 Read View 何时创建？

在读提交下，每条普通一致性读通常创建新的 Read View，所以后一条查询可看到期间新提交的修改。在可重复读下，通常在事务第一次一致性读时建立视图，后续一致性读复用它；`BEGIN` 本身不等于已经为普通查询拍好了快照。

RR 下使用 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 可以在开启时建立一致性快照。这个规则不能套给 `UPDATE`、`DELETE` 或 `SELECT ... FOR UPDATE`，它们需要依据当前记录和锁进行处理。自己的更新也可能被本事务后续读取看到，所以“事务中任何查询永远看同一份数据”过于绝对。排查时应记录第一条快照读发生的时间，并检查连接是否一直没有提交。

## Q05 快照读与当前读有什么区别，RR 是否完全杜绝幻读？

在 RC、RR 下，普通 `SELECT` 通常是快照读，读取 Read View 可见的历史版本；`SELECT ... FOR UPDATE`、`FOR SHARE` 及更新删除相关操作属于当前读，会按操作申请锁，遇到冲突锁可能等待。当前读不能理解为直接读取别人的未提交数据。

RR 中，持续使用同一快照可保持查询视图稳定；从一开始就对目标范围做适当锁定读，可阻止其他事务向受保护间隙插入。但先做快照读、后做当前读，或本事务更新了原先不可见的新记录，观察到的集合可能变化。业务若要“检查不存在后插入”，应结合唯一约束和明确的并发控制，不能仅凭默认隔离级别保证不重复。

## Q06 行锁、表锁、意向锁和 MDL 分别保护什么？

InnoDB 行级锁主要作用在索引记录或索引间隙上，记录锁有共享和排他模式。意向锁是表级标记，用于表达事务准备持有行级共享锁或排他锁，帮助表级操作快速判断冲突；它不等于把整张表的数据都锁死，也不应与插入意向锁混淆。

显式表锁约束整表访问，MDL 元数据锁则保护表结构，普通查询同样会取得相应 MDL，避免使用中的结构被并发修改。长事务不结束可能让 `ALTER TABLE` 等待，即使它没有更新数据。定位时要先区分等待的是行锁还是元数据锁；一个查询没走合适索引而锁住大量记录，也不应简单描述为“自动升级成了表锁”。

## Q07 间隙锁、临键锁的范围怎样理解，唯一等值查询有什么区别？

记录锁保护已存在的索引记录，间隙锁保护两条索引记录之间的空隙以阻止插入，临键锁是两者结合，通常表示左开右闭的区间。间隙锁之间可以兼容，不意味着拿了间隙锁就能自由插入；插入仍需与其他事务已持有的间隙保护协调。

在 RR 下，对完整唯一键做等值锁定查询，命中现有记录通常可只加记录锁；查找不存在的值可能锁住其所在间隙。非唯一索引或范围扫描则可能保护更宽范围，二级索引访问也可能涉及聚簇记录锁。RC 通常减少搜索用的间隙锁，但外键和重复键检查等仍有例外。实际范围以访问路径及 `performance_schema.data_locks` 为准。

参考：[MySQL 是怎么加锁的？](https://xiaolincoding.com/mysql/lock/how_to_lock.html)

## Q08 MySQL 死锁如何产生、排查和处理？

死锁是多个事务形成等待环，例如甲已锁第一行再等第二行，乙已锁第二行再等第一行；先查不存在再插入，也可能因间隙锁与插入意向形成死锁。普通锁等待不一定是死锁，延长等待时间不能消除等待环。

可查看 `SHOW ENGINE INNODB STATUS`、锁等待关系及相关事务 SQL，结合索引和访问顺序分析。启用死锁检测时，InnoDB 通常选择一个事务回滚，应用应回滚整理连接状态，再对整个业务事务做有限重试。固定加锁顺序、缩短事务、减少扫描范围、用唯一约束表达唯一性均有帮助。重试还要约束外部副作用，不能只重发最后一条 SQL 或无上限重试。

参考：[MySQL 死锁了，怎么办？](https://xiaolincoding.com/mysql/lock/deadlock.html)

## Q09 undo log、redo log、binlog 的职责有何不同？

undo 属于 InnoDB 的撤销信息，用于事务回滚，并帮助 MVCC 重建历史版本；redo 记录恢复数据页修改所需的信息，用于崩溃恢复；binlog 位于 Server 层，记录逻辑变更事件，主要用于复制和时间点恢复。三者解决的问题不同，不能互相替代。

数据页会先在 Buffer Pool 中修改为脏页，再按策略写回。WAL 的关键约束是相关 redo 要先于脏页持久化，并不是每次更新都立即把整页写盘。尚未提交的修改也可能进入磁盘，恢复时仍需处理未完成事务，不能认为“宕机后内存一丢就自然回滚”。更新或删除产生的 undo 也不一定提交即删除，还要等旧快照不再需要，由清理流程回收。

参考：[MySQL 日志：undo log、redo log、binlog 有什么用？](https://xiaolincoding.com/mysql/log/how_update.html)

## Q10 redo 与 binlog 为什么需要两阶段提交，双一参数能保证什么？

开启 binlog 时，同一个事务既影响引擎恢复状态，又影响复制日志，若两份日志对提交结果判断不同，就可能让本机恢复和从库重放产生分歧。内部两阶段提交通过 prepare、binlog 持久化与 commit 等步骤协调，并在崩溃恢复时根据事务标识和日志完整性作出提交或回滚判断。

`innodb_flush_log_at_trx_commit=1` 与 `sync_binlog=1` 通常称为双一，要求提交相关日志按策略同步持久化，可配合组提交减少开销。它们依赖底层存储兑现持久化语义，不保证误删后自动恢复，也不保证异步从库已经收到每笔事务。备份、复制延迟监控和恢复演练仍有各自作用，不能把参数配置说成“任何故障都零丢失”。
