# Java 面试知识库：Redis 缓存一致性与并发

整理日期：2026-11-11。本文依据小林 coding 公开资料编写，是原创学习总结，非官方原文。“高频”代表备考优先级，不是统计排名。示例以 Redis 6/7 和关系数据库组合为背景；缓存一致性、锁的互斥与故障恢复都需要明确边界，不能作无条件保证。

## Q01 Cache Aside 为什么常用先更新数据库，再删除缓存？

旁路缓存的读流程是先查缓存，未命中再查数据库并回填；写流程通常先成功提交数据库事务，再删除相应缓存。删除比主动重建聚合数据更轻，也避免两个并发写请求按不同顺序更新缓存而留下旧值。数据库是权威数据源，缓存是允许失效后重建的副本。

这个顺序仍不是强一致协议：一个慢读可能在数据库更新前取得旧值，等新事务提交并删缓存后才把旧值写回；删除失败也会留下旧缓存。TTL、可靠失效和版本判断可以约束风险，但要说明收敛的前提。账户余额等必须即时正确的决策应访问权威状态并使用事务保护，不能把“先库后删”说成任意并发与故障下都一致。

## Q02 缓存删除失败怎样补偿，延迟双删能保证一致性吗？

删除失败应有可靠、可观测的重试来源，例如数据库事务内写入待失效事件，再由后台投递；也可订阅 binlog 驱动缓存失效。消费者成功删除后再确认，处理重复事件并监控积压、失败和最长滞后。若数据库已提交但连“重试事件”都没持久化，进程退出就可能永远漏删。

延迟双删是隔一段时间再删一次，试图覆盖慢读回填旧值的窗口；睡眠时长无法覆盖所有网络延迟、暂停和副本滞后，因此只能减少特定竞态，不能证明强一致。TTL 同样是兜底而非瞬间一致，过期前仍可能读旧值。需要更严格语义时，应结合版本控制、串行化访问或直接读取数据库，并说明额外成本。

## Q03 缓存穿透是什么，空值缓存与布隆过滤器有什么边界？

缓存穿透是请求的数据在缓存和数据库都不存在，导致不断回源却无法用正常值建立缓存。可先做参数校验、鉴权和限流，再对确定不存在的结果缓存短期空值，或用布隆过滤器在回源前判断成员是否可能存在。空值应与系统错误区分，数据库超时不能缓存成“对象不存在”。

标准布隆过滤器对已经正确加入的集合没有假阴性，但有假阳性；实际数据库新增未及时加入过滤器时，仍会出现业务层误拦。空值缓存也可能短暂遮住后来新增的数据，需要失效或合理 TTL。Redis 6/7 的基础服务不能默认假定安装了 RedisBloom 扩展，是否有相应命令要查部署；位图、自建过滤器也需要维护容量和更新流程。

参考：[什么是缓存雪崩、击穿、穿透？](https://xiaolincoding.com/redis/cluster/cache_problem.html)

## Q04 热点缓存击穿如何解决，互斥重建要注意什么？

击穿通常是某个被密集访问的热点键失效，许多请求同时回源。可对同一键合并重建请求：拿锁者再次检查缓存，仍缺失才查库回填；其他请求做有界等待后重读，或者按业务容忍度返回旧值。锁等待失败不能无条件各自查询数据库，否则保护在高峰时失效。

逻辑过期可以保留旧值，由一个后台任务刷新，以可用性换取短时间陈旧；它不适合所有强实时数据，且首次没有旧值时仍需处理冷启动。重建锁还需要持有者标识、租约和正确释放，业务执行超过租约时应防迟到回填覆盖新值。单进程请求合并只能约束本实例，多实例是否共享锁要结合回源容量设计。

## Q05 缓存雪崩和击穿有什么区别，Redis 故障时能全部回源吗？

雪崩关注大量键同时失效或整个缓存服务不可用，击穿主要集中于单个热点键。批量到期可通过在 TTL 上增加随机偏移、预热和错峰刷新降低集中压力；缓存实例故障则需要高可用、连接超时和熔断等措施，给 TTL 加随机数解决不了整台 Redis 不可达。

故障时不能默认把全部流量放到数据库，原本被缓存吸收的请求可能瞬间超过数据库容量。应按业务优先级设置回源并发上限、有限重试、降级或旧值服务，必要时拒绝部分请求。恢复后也要分批预热，避免所有实例一起抢建缓存。持续监控命中率、回源量、数据库连接池和尾延迟，才能区分缓存冷启动与缓存故障。

## Q06 过期删除与内存淘汰有什么区别，LRU 和 LFU 怎么选？

过期删除处理已经到达 TTL 的键，Redis 结合访问时检查和主动周期清理，不保证到期瞬间就物理释放内存。内存淘汰是在达到 `maxmemory` 等条件时，按策略挑选键回收，可能删除尚未过期的键。因此“没有过期时间”不代表不会被淘汰。

`allkeys` 策略考虑全部键，`volatile` 策略只在设有过期时间的键中选择；`noeviction` 通常拒绝需要增加内存的写操作，并非让所有查询停服。LRU 关注最近访问，LFU 结合访问频度与衰减，Redis 实现带有采样或近似机制。选择要看访问分布并观察命中率，不能断言 LFU 永远更好；锁、不可重建状态和普通缓存混用时尤其要审查淘汰风险。

## Q07 Redis 分布式锁为什么需要原子加锁、唯一值和 Lua 解锁？

可用 `SET lock:key owner NX PX 30000` 把不存在时设置和租约一起完成，避免分开 `SETNX`、`EXPIRE` 期间崩溃留下无期限锁。每次持锁使用唯一 owner，释放时用 Lua 原子比较 owner 并删除，不能先 GET 再 DEL，更不能无条件删锁，否则可能删除已经属于别人的新锁。

租约到期不会强制停止旧业务线程，看门狗续期也可能因暂停或网络故障失败。需要防旧持有者迟到写入时，应由资源端校验版本、状态或可靠的 fencing token；主从异步复制后的故障切换也可能丢失锁记录。锁可以减少竞争，但订单唯一性、库存约束等最终业务正确性还要由数据库约束或条件更新兜底。

## Q08 Lua、MULTI/EXEC、WATCH 和 Pipeline 分别解决什么？

Lua 适合把依赖前一步结果的判断与修改放在服务端执行，在执行期间避免其他普通命令插入。`MULTI/EXEC` 将命令排队后一并执行，`WATCH` 可检测关注键是否变化并让事务放弃，Pipeline 主要减少网络往返，并不把一组命令自动变成隔离的事务。

Redis 的事务或脚本不提供关系数据库那样的通用回滚：执行阶段出错时，已完成的写入不会自动撤销，因此应先验证参数和键类型，再开始修改。原子执行也不等于已经持久化或复制成功。长脚本会占用命令执行线程，多键操作在 Cluster 中还受同槽等限制。设计扣减库存时，既要检查非负条件，也要考虑客户端超时后不知道结果而重复提交。

## Q09 主从复制、Sentinel、Cluster 的职责和一致性边界是什么？

主从复制让副本跟随主节点的数据变化，Sentinel 负责监控和主从故障转移，Cluster 通过槽把键分布到多个主节点并配合副本。它们分别涉及数据冗余、故障检测和容量分片，不能把“有哨兵”当成数据已经分片，也不能把副本数量当作可线性增加的写吞吐量。

常见复制是异步的，主节点已响应而副本还没收到的修改，在故障转移时仍可能丢失；从库读取也可能滞后。Cluster 使用 16384 个槽，多键脚本、事务等需要考虑键是否在同槽，可通过 hash tag 组织，但也可能形成热点。提高副本数量和复制等待可减少部分风险，不能由此承诺强一致或零丢失，更不能用实时副本替代历史备份。

## Q10 BigKey 与 HotKey 有什么区别，怎样定位和治理？

BigKey 是单个值很大或集合元素很多，HotKey 是某个键访问特别密集，两者可以同时出现。大键容易放大序列化、网络传输、遍历、删除和持久化成本；热点键即使很小，也可能让某个节点的请求量和带宽过载，平均分配槽并不能自动拆散同一个热键。

定位可结合慢日志、命令统计、采样扫描、`MEMORY USAGE` 和访问指标，避免在线上直接用 `KEYS *` 或一次读取整个大集合。治理包括分页访问、拆分数据、设置合理上限、对热点做本地缓存或请求合并。`UNLINK` 可把适合异步回收的内存释放移出主线程，但不会消除所有解析、网络和持久化成本；拆分也要保留业务所需的原子边界。
