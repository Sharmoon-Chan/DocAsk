# 问档 DocAsk 工程案例（2026-11-11 v10 原文交付版）

问档在开源 JChatMind 基础上改造了执行、权限、索引和答复交付。下面用具体问题说明机制与边界；历史演练说明对应环境中的观察，不作为吞吐能力或服务时延承诺。

## 案例一：重复提交为什么不会新建两次运行

网络超时不等于服务器没有受理。问档按“身份、会话、幂等键”识别一次提交意图，用户消息、输入快照、运行记录和队列任务在同一事务中保存，并由数据库唯一约束兜底。

同一个键和相同内容再次提交会取得原运行，同键内容不同则拒绝；一个会话也不能同时存在两个排队或运行中的任务。同机双实例演练中，同键依次发给两个实例共三次，取得同一运行；同会话用不同键并发提交时，一个受理、一个冲突。

这里避免的是重复提交生成重复运行。模型请求可能按故障类型进行有限重试，所以不能把它扩展成所有模型或外部服务调用的 exactly-once。

## 案例二：取消和租约失效怎样挡住迟到写回

取消请求先被持久化，后台在检查点停止继续执行。已经发出的模型请求不一定能够撤回，但取消后不能继续把迟到结果当作正常答复。

写消息时在同一事务中锁定任务行，检查 RUNNING 状态、fencing token、取消标记和租约期限，再写消息及最终答复关联。写入也可能等待其他数据库行，因此完成相关写入后还要复查租约；不满足条件就回滚整笔写入。成功终态也在写入前后检查相同的成功条件。

期限判断使用 PostgreSQL 的 clock_timestamp()，因为事务中的 NOW() 固定在事务开始时刻，不能反映等待期间已经过去的时间。取消或中断终态仍可写入，不会因为用于成功执行的租约已经失效而无法收尾。

状态、取消与期限检查各有作用。对话任务领取后不自动重放，fencing token 不会像可重新领取的导入任务那样不断前进，不能把所有迟到保护都归因于 fencing。先完成还是先取消，以持锁事务实际提交的结果为准；后来的取消不撤销已经提交的正常答复。

## 案例三：进程重启后哪些任务能够继续

尚未执行的 QUEUED 任务已经持久化，服务启动后可由 worker 继续领取。领取使用包含 FOR UPDATE SKIP LOCKED 的更新语句，多个 worker 跳过其他事务已锁定的候选任务。

RUNNING 任务若失去执行进程，在租约过期后记为中断，不自动重放，因为外部调用可能已经发生，系统无法证明整轮重跑不会重复。如果任务此前已经登记取消，过期处理保留取消语义。

2026-10-18 的演练使用同机两个独立 JVM 和一个 PostgreSQL 库。租约临时压到20秒，强行终止执行进程后，另一实例约22.1秒后将该运行标为中断，没有自动重放。默认租约为120秒，不能把22.1秒当作线上恢复承诺；跨主机、网络分区和时钟漂移没有在这次演练中验证。

## 案例四：行锁等待和线程中断为什么不能忽略

心跳、消息落库和终态更新都可能等待数据库锁。一个任务若堵住共用心跳线程，会牵连其他运行；一次写入若跨过租约期限，也不能因为进入事务时还有效就继续成功提交。

问档为每个运行提供独立的心跳调度，续租走独立连接与短事务并限制锁等待。检查点遇阻时先在预算内重试，再读取状态与期限确认能否继续；可能阻塞的更新之后再次核验。锁冲突严重时允许失败或中断，不采用无限等待。

模型节流和重试等待也会分段检查运行状态。线程中断、取消或租约丢失时停止等待和后续请求；这些控制信号不能被模型故障的回退逻辑吞掉，也不能在收到迟到响应后继续写正常答复。

## 案例五：后台执行按谁的权限检索

任务可能排队，也可能由另一进程领取，因此后台不依赖原 HTTP 请求线程的登录上下文。提交人的身份和账号版本随任务持久化，领取时重新核对账号、会话、助手与模型，并比较提交时保存的助手配置哈希。

排队期间模型、提示词、工具或知识库范围变化时，拒绝执行，不悄悄换用另一份配置。每次工具调用前再次校验执行权限，知识库参数必须落在助手获准范围内，游客还受公开知识库白名单限制。

原文参考回退同样使用受限的 KnowledgeTool，不直接扫描数据库中的任意资料；它不会换用其他人的权限，也不会调用邮件、数据库或文件系统工具。权限复核能停止后续行为，但不能撤回已经发出的外部请求。

## 案例六：怎样处理编号合法却指错段落的问题

旧式交付让模型同时维护自由正文和引用数组。编号在合法范围内，只能说明它指向某条来源，不能证明这条来源支持正文；即使额外检查一段短引存在于原文，也不能据此验证任意改写。

公开执行器改用 sourceAnswer。模型提交最多三个 citationId、各自片段中的连续原文锚点及可选 full/partial 覆盖状态，不提交 answer、text、reason 或自编编号。服务端检查来源身份、锚点和访问范围，按真实来源去重编号，完整展示选中命中的正文。编号与正文从同一个来源记录产生，不再由模型配对两套内容。

输出明确称为“资料原文”。片段内的否定、条件和例外会一起保留，不因模型改写而被删成无条件结论。代码、HTML和原有数字标记作为原文显示，不充当新的回答引用。这个机制不判断原作者是否正确，也不保证选中片段足以回答所有问题。

只覆盖部分版本、数据或子问题时，coverage 必须选择 partial，服务端附加固定的部分覆盖提示；省略覆盖字段按 full 处理。没有可支持部分时，insufficient:true 与 sources、coverage 互斥，而且必须先真实检索。非法类型、未知覆盖值及自由原因字段被拒绝。覆盖声明仍来自模型，固定提示不构成语义证明。

## 案例七：模型没有正确交付时，怎样避免空答复成功

需要知识回答时先实际检索，再单独使用 sourceAnswer 交付来源，或在真实检索后返回不足信号。同一批次混合 KnowledgeTool 与最终交付会先被拒绝，不会先执行一部分工具或在证据尚未取得时落答案。

格式、来源 ID 或锚点无效时，系统给一次修正机会。再次无效或适当模型故障后，已有本轮登记检索来源时可以交付明确标注的“原文参考”，不要求模型此前已经成功交付sourceAnswer。如果没有既有本轮来源且此前尚未完成可读检索，服务端仍用原始问题执行正常受限 KnowledgeTool检查可读性，但不发布这次服务端读取的近邻，只给固定服务未完成/未确认提示。已有可读的无匹配检索不被重复执行。没有可用工具、获准知识库或可读检索时报告失败，不能伪装成已经查过资料。

正常不足提示必须发生在真实检索之后；NO_MATCH 表示该次检索没有匹配片段，已有片段也可能不足以确认问题。服务调用失败不是NO_MATCH，也不能证明整个知识库不存在相关知识。真实不足、正常原文、部分覆盖、参考回退和服务未完成是不同的结果，运行有交付不能单独算问题答对。

达到20步上限仍未交付内容时，运行记为 ERROR，不再把循环结束等同于有答复。只有日期的问题在 getDate 成功后可由服务端直接展示实际日期；同时包含日期和知识点的问题会继续检索，最后保留日期与原文资料，不以单个日期提前结束。

## 案例八：模型故障为什么需要分类与有界处理

连接问题、读取超时、限流、上游服务故障和返回内容无法解析，不是同一种错误。问档根据可取得的状态码和异常类型分类，在有限预算内重试适合重试的请求，并记录安全的诊断信息；不会把所有失败都归因于429。

对历史记录只报已知事实：一次验证中的5次模型失败，只有1次具有明确的429证据，其余旧记录不足以确定具体原因。本版增加分类和调用记录，是为了让后续故障能够区分，而不是补造旧故障的原因。

模型仍无法完成时，已有本轮真实检索来源可以给出未确认的原文参考，来源存在不等于相关性已经验证。此前没有既有本轮来源时，必要的服务端读取只检查可读性，不发布这些任意近邻。回退不重复执行已完成工具，也不尝试外部副作用。未知编程异常、运行取消、租约失效和线程中断不能被包装成正常回退成功。

## 案例九：失败的旧问题如何进入下一轮

失败、取消或中断的运行可能只留下用户提问。直接拼接历史会让旧问题看起来仍待执行，旧工具结果也可能被误用为本轮证据。

问档按运行整理输入：已回答轮次保留相关上下文，未完成旧轮只把提问作为背景，丢弃其工具结果，并说明它不是当前待办。本轮来源登记只接受本轮实际执行后的检索返回。用户仍可以明确要求重答上一题，这种情况下会重新取证。

## 案例十：检索分数下降时怎样区分实现与计分问题

从标题向量改为正文分块后，旧 frozen-v1 判据下 Hit@3 从0.850降到0.600。旧判据要求片段行号包含标题行，而正文片段从正文开始计行、标题保存在章节路径，因此两种表示的证据定位不同。

项目保留旧判据与旧结果，另行冻结 body-window-v2：核对证据正文、所需事实与章节标题，不再要求标题必须落在正文片段的行号范围内。两组已保存检索结果按同一新口径重新计分，没有重跑向量模型或数据库。

在50题冻结集的40道有答案题上，标题索引与正文索引的 Hit@1 分别为0.650、0.875，前三条结果的证据单元覆盖分别为34/44、43/44。新口径是看过旧结果后提出的诊断口径，不能作为事先设定的独立盲测。

当前仍存在排序、干扰片段与资料不足处理的改进空间。混合检索和重排尚未实现，向量距离拒答阈值未启用；新增100题学习资料另行维护，不属于这组历史评测语料，原文交付也不会自动提升这些检索指标。

## 案例十一：请求间隔怎样进入实际游客运行

仅在配置里填写模型请求间隔，不保证手工创建的对象已经接入节流。游客执行器曾手工new运行工厂，而门控依赖Spring字段注入，手工对象因此保持默认NONE。现在容器工厂和游客工厂都要求显式传入同一个必需的ModelRequestGate，并由实际公开运行时回归验证发送前预约门控的路径。

发送前的节流等待和重试退避分片检查取消、租约失效及线程中断。后续重试所需时隙超过20秒重试开始窗口时不再发送该请求；这不是整轮运行的20秒期限。候选验证采用10秒请求间隔、单worker配置，这属于调用压力控制，不是检索算法改进，也不能保证上游永远不会限流。

## 案例十二：同步调用期限和受限传输执行器

连接5秒、HTTP读取30秒不能单独保证整次模型调用最多30秒。新实现用ModelCallDeadline包住每次同步供应商调用，期限取LLM读取设置，当前为30秒；调用方等待到期后取消Future，拒绝迟到结果继续进入Agent交付。发送前节流等待和Agent的多步循环不在这一次请求预算内。

一个模型运行服务的客户端共享最多4个传输执行槽，使用无等待队列的交接方式。供应商忽略中断时仍占用原槽直到实际返回，不会不断创建替代线程或堆积排队。槽耗尽返回安全的不可用诊断；超时取消不承诺远端请求立即停止，但已经取消的Future不会把晚结果交回调用方。

默认模型选项关闭内部自动工具执行，显式要求开启也会被拒绝。传输线程只调用供应商，Agent工具执行、权限检查与消息写入仍在调用线程及正常守卫下完成，不能让迟到模型在内部执行工具或写数据库。

## 案例十三：复合问题的原文参考怎样分配预算

把各次检索的第一名混成一个总体排名，或直接取最早一组的前三条，都可能让一个子问题占满参考预算。参考选择现在按本轮实际完成的检索序号分组，先从每组取一条，再轮流补下一排名候选，并执行授权过滤与同一来源范围去重，最多保留三项。

这个机制让多组已完成检索有机会被保留，减少第一组挤掉另一子问题证据的情况。它不比较不同查询的语义置信度，不证明原文一定相关或问题已答全；超过三项预算时仍可能缺项。输出始终注明自动整理未完成和原文参考，不能称为经过语义核验的完整答案。

## 案例十四：正文分块为什么必须严格前进

合法小文档也可能让分块循环失去进展。一个段落自身能放进预算，但与下一段合并会超预算时，当前块可能只包含一个atom，即`last == first`。原`nextStart`重叠起点计算在这条分支返回原index，外层while再次输出完全相同的Range，持续追加直到Java堆内存耗尽。原文解析正常和单块大小有界，都不能证明整个循环会结束。

修复要求下一起点严格大于first：重叠起点本来已前进时保留它，否则使用`first + 1`。当前atom已经包含在输出块中，因此继续到下一个atom既不会重发同一块，也不跳过尚未处理的内容；可保留的重叠仍在预算内处理。

本地检查覆盖独立段落能放下但合并超预算、重叠配置及相邻内容覆盖，既验证有界完成，也验证没有无限重复同一Range或漏掉必要内容；正常预算内的重叠仍可保留。触发原件保持不变，在受限堆回归中能够完成分块，并通过预算和行号检查。不能通过缩短文档绕开缺陷；实际导入与生产结果仍按发布记录验收，不预报上线收益。
