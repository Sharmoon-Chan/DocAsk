# 问档 DocAsk 工程案例（2026-11-11 版）

本文说明问档在开源 JChatMind 基础上新增的执行、权限、答复与检索机制。案例依据已保存的代码和验证记录；历史演练结果只说明对应环境下观察到的行为，不代表吞吐能力或线上服务承诺。

## 案例一：重复提交为什么不会新建两次运行

网络超时不等于服务器没有受理。如果用户重试时每次都创建新任务，就可能产生重复消息和额外模型调用。

问档把一次提问表示为带幂等键的提交意图，按“身份、会话、幂等键”去重。用户消息、固定历史快照、运行记录和队列任务在同一个事务内保存，数据库唯一约束负责兜底。同一个键和内容再次提交，返回原运行；同键内容不同则拒绝。同一会话也不允许同时存在两个排队或运行中的任务。

在同机双实例演练中，同一个键依次发给两个实例共三次，取得的是同一个运行；同会话以两个不同键并发提交时，一个受理、一个冲突。这里保证的是提交意图不会产生重复运行，不是模型或外部服务调用的 exactly-once；执行过程中的请求重试仍可能发生。

## 案例二：取消后迟到的答复怎样处理

取消是协作式的，已经发出的模型请求无法保证立即撤回。问档先登记取消请求，后台在检查点停止继续执行，最后写入取消终态。

写消息和最终答复时，服务端在同一事务内锁定任务行，确认任务仍处于 RUNNING 且 fencing token 匹配，再写入消息及答复关联。已取消、已中断的运行不能再写入正常答复。取消与完成同时发生时，以实际提交的终态为准；已经完成的答复不会被后来的取消请求撤销。

状态检查是当前对话队列拦截迟到写回的关键。对话任务领取一次后不自动重放，fencing token 不会像可重新领取的导入任务那样不断前进，不能把所有保护都归因于 fencing。

真实 PostgreSQL 用例覆盖正常写回、中断后回滚和失效执行者写回被拒等路径；长模型调用的取消演练也核对了迟到响应不会追加为正常答复。取消不撤销已经发出的外部请求，更不承诺立即停止外部计算或计费。

## 案例三：重启后哪些任务能够恢复

尚未开始的 QUEUED 任务已经与用户消息一起持久化，服务启动后可由 worker 继续领取。领取使用一条包含 FOR UPDATE SKIP LOCKED 的更新语句，多个 worker 跳过已被其他事务锁定的候选任务。

已经开始的 RUNNING 任务若失去原执行进程，会在租约过期后记为中断，不自动重放；原因是模型调用、工具调用及其副作用可能已经发生，系统无法证明重试不会重复。如果任务先前已经登记取消，过期处理会保留取消语义。

2026-10-18 的演练使用同一台机器上的两个独立 JVM 和同一 PostgreSQL 库。租约临时压到20秒后，强行终止执行进程，另一实例约22.1秒后将运行标为中断；该轮没有半截助手答复，也没有自动重放。默认租约是120秒，不能把演练的22.1秒当作线上恢复时延。跨主机、网络分区和时钟漂移没有在这次演练中验证。

## 案例四：数据库行锁为什么会影响模型执行

心跳、续租和消息落库都可能等待数据库行锁。如果多个任务共用一个心跳线程，一个任务的锁等待就可能拖住其他任务；如果检查点在等待后直接放行，任务还可能带着过期租约继续调用模型。

问档为每个运行提供独立的心跳调度器，续租走独立连接与事务，并限制锁等待时间。执行检查点遇到阻塞时，先在预算内重试，再通过不加锁的读取确认状态、fencing 和租约期限；确认不了就停止。运行摘要的心跳更新同样有界，并在可能阻塞的写操作后复查租约。

数据库回归用例覆盖了单个任务行锁不拖住其他任务、检查点等待期间租约到期、摘要心跳写入受阻等场景。这是正确性保护，不是吞吐优化；锁冲突严重时，任务可能失败或中断，不能承诺无限等待后继续执行。

## 案例五：后台执行按谁的权限调用工具

任务可能排队，也可能由另一个进程领取。后台不能依赖原 HTTP 请求线程的登录上下文，更不能直接相信模型生成的知识库 ID。

问档将提交人的身份信息和账号版本随任务持久化。领取时重新核对身份、会话、助手和模型是否可用，并比较提交时保存的助手配置哈希。排队期间助手的模型、提示词、工具或知识库范围发生变化时，拒绝执行，不悄悄使用另一份配置。

每次工具调用前再次复核执行权限。知识库参数必须落在助手获准范围内；游客检索还需要通过公开知识库白名单检查。跨账号、跨访客访问和参数越界有端到端或单元测试覆盖。

复核可以拒绝后续执行，但不会撤回已经发出的模型请求，也不会换用其他人的权限重试。

## 案例六：为什么用专用工具交付最终答复

Agent 决策轮可能产生“先检索一下”等过程文字。把每轮模型正文直接当作最终回答，会混淆过程与交付；模型主动结束但没有答复时，也不能仅凭循环结束判定成功。

问档通过 directAnswer 工具交付最终答复，答案放在工具参数中，中间轮的模型正文不作为最终答复。模型主动结束本轮却没有交付时，会增加一次收尾机会；补轮后仍未交付，则记录失败。模型和工具调用另存为运行事件，便于查看。

该完成判定有明确范围：Agent 跑满20步上限的分支仍可能记为成功但没有答复，不能概括为“所有无答复情况都会失败”。专用通道分离了决策文本和最终交付，也不能保证模型没有在答复参数中写入无关内容。

## 案例七：上一轮失败的提问如何进入下一轮

失败、取消或中断的运行可能只留下用户提问。若简单拼接消息，这个悬空问题可能被模型当作尚待执行的任务，历史检索结果也可能被误认为本轮证据。

问档按运行整理输入历史。已回答的轮次保留相关上下文；未完成的旧轮仅保留用户提问作为背景，丢弃旧工具结果，并说明它不是当前待办。本轮回答的引用登记只接受本轮真实返回的检索结果。

单元测试覆盖了失败轮、取消轮与正常轮混合时的输入整理。该处理不修改已保存的历史，也不妨碍用户明确要求重答上一题；它减少输入歧义，不保证模型永远不会错误理解指代。

## 案例八：检索分数下降时，怎样判断是实现问题还是计分问题

上游只对章节标题生成向量，问档改成正文分块后，旧冻结判据的 Hit@3 从0.850降到0.600。直接据此断言正文检索更差，会漏掉证据定位的差异：旧判据要求片段行号包含标题行，正文片段却从正文开始计行，标题保存在章节路径中。

项目保留旧判据和旧结果，另行冻结正文窗口 body-window-v2 口径：核对正文行、要求的事实和章节标题，不再要求标题必须落在正文片段的行号范围内。新旧两组保存的检索结果都按同一新口径重新计分，没有再次调用向量模型或数据库。

在50题冻结集的40道有答案题上，Hit@1由0.650提高到0.875；前3条结果覆盖的证据单元由34/44增加到43/44。新口径是看过结果后定义的，不能冒充事先设定的独立验证；完整定义和新旧结果均保留。

这组数据仍暴露出排序、干扰片段和无答案题处理的问题。当前没有接混合检索或重排，检索级拒答开关未启用；下一步的效果需要另行测量，不能由现有小样本推断。新增八股学习资料也不属于这组历史冻结评测语料。
