# 问档 DocAsk 工程案例（2026-11-09 版）

本文用「问题 → 方案 → 验证结果 → 边界」的结构讲七个真实的工程案例，全部来自本仓库的实现与测试记录。
核对日期：2026-11-09。文中耗时与用例数量都是当次真实输出，不代表长期性能承诺。

## 案例一：重复点击发送，会不会跑两次

**问题**：网络慢的时候用户会连点发送，或者请求其实已经到了服务器、只是响应丢了。如果后端每收到一次就执行一次，
会出现两条用户消息、两次模型调用、两笔费用，甚至两条不同的回答挂在同一个问题上。

**方案**：把「一次提问」变成带唯一键的提交意图，服务端按 `(身份, 会话, 幂等键)` 去重。

- 前端为每个「新的提问意图」生成一个键，重试与重连复用同一个键，只有用户明确问下一个问题才换键。
- 提交在一个事务里完成：写用户消息、固定历史快照、创建运行记录、入队。同一个键再次到达时不再新建运行，
  而是返回原来那次运行的 `runId` 与状态。
- 同一个键但内容不同则直接拒绝，避免拿旧结果冒充新请求。

**验证结果**：真实 PostgreSQL 集成测试断言同键并发只产生一次运行、返回同一个 `runId`；同键不同内容返回冲突。
双实例演练中，同一个键先后发到两个实例共三次，三次都返回同一个 `runId`，只执行了一次；同一会话用两个不同的键
同时提交，一个被受理（200），另一个返回冲突（409），因为一个会话同一时间只允许一个进行中的运行。

**边界**：这只保证「同一会话的同一提交意图最多执行一次」，不是对外部调用的 exactly-once 承诺。
模型请求和工具调用本身仍可能被重复发出，系统保证的是结果写入与终态唯一且受校验。

## 案例二：点了取消，模型又迟到返回

**问题**：取消是个协作式动作。已经发出去的模型请求无法撤回，几秒后它可能仍然返回一段完整答案。
如果不加约束，运行已经被标记为取消，答案却又被追加到会话里，用户看到「已取消」后面又多出一段回答。

**方案**：把「请求取消」和「运行终态」分开，并给每一次执行加 fencing 校验。

- 运行中的取消只登记 `cancel_requested`，检查点在下一个步骤前停止发起新的工具或模型调用，最终记为
  `CANCELLED / CANCELLED_BY_USER`。
- 每次领取任务都会让 `fencing_token` 前进。写答案时必须同时满足「任务行仍是 RUNNING」「fencing 未被接管」
  两个条件，答案消息与 `answer_message_id` 在同一个事务里写入；条件不满足就整笔回滚，迟到的内容一个字都不留。
- 取消与完成竞争、取消跨过心跳周期、重启遗留的 RUNNING 都有各自的判定，不会互相顶替。

**验证结果**：真实 PostgreSQL 用例覆盖三条路径：运行被标记中断后写答案必须抛出租约丢失并回滚；正常运行时
答案与关联同事务落库；租约被接管后旧执行写不回任何内容。另有一条 18 秒模型调用、10 秒租约的用例，取消后
终态为 `CANCELLED`，迟到响应不追加答复。

**边界**：取消不撤回已经发出的外部请求，也不承诺「立即停止」。界面显示「正在取消」，直到运行状态真正变成终态。

## 案例三：服务重启时，排队任务和运行任务如何处理

- **QUEUED（尚未开始）**：任务和用户消息已经持久化；服务重启后，worker 会重新领取尚未开始的排队任务。
- **RUNNING（已经开始）**：原 worker 因重启消失后，租约过期，运行记为 `INTERRUPTED / INTERRUPTED_BY_RESTART`。
  不自动重放结果未知的模型或工具调用，因为它们的副作用无法回滚，重放就是重复执行、重复计费。
- **已经登记取消**：运行仍在处理中且 `cancel_requested=true` 时，过期扫描记为 `CANCELLED / CANCELLED_BY_USER`，
  不会误标为重启中断。
- **已经完成**：取消请求不会撤销已经提交的完成终态；响应里的「已结束」不能解释成「取消成功」。

上述状态转换由真实 PostgreSQL 队列用例、独立 JVM 重启与 HTTP 取消演练核对。双实例演练中，强行终止正在执行的
进程后，约 22 秒由另一个实例把运行记为 `INTERRUPTED_BY_RESTART`；会话里没有半截回答，也没有自动重放。
「恢复」指重新领取尚未开始的任务或读取已保存的记录，不是从任意一次外部调用中间无重复地续跑。

## 案例四：一个任务的行锁，为什么会连累别的任务

**问题**：租约续期、心跳、写消息都是对数据库的写操作。当某一行被一条慢事务锁住时，续期会卡在锁上。
如果多个运行共用同一个后台线程，一个任务的锁等待就会拖住所有任务的心跳，别的运行被误判成中断。

**方案**：把「锁等待」变成有界、可放弃的动作，并且每个运行独立。

- 每个租约使用自己的单线程调度器，心跳续期走独立连接、独立事务和 `SET LOCAL lock_timeout`，
  被锁挡住只会跳过这一拍，不会把运行判成租约丢失。
- 执行检查点如果被锁挡住，先在预算内重试；预算耗尽后用一次**不加锁的读**确认状态、fencing 与租约期限。
  确认不了就停止执行，绝不再发起新的模型调用。
- 摘要心跳也改成有界写，写完再确认一次，最终确认之后不再执行任何可能长时间阻塞的数据库写入。

**验证结果**：真实 PostgreSQL 用例固定复现三类场景：A 的消息事务持锁 16 秒时，B 的 22 秒模型调用仍正常完成；
检查点在锁等待中租约到期必须抛出租约丢失；摘要心跳被锁挡住时按预算放弃，而不是无限等待。

**边界**：这些是正确性与成本保护，不是吞吐优化。行锁冲突频繁时，运行会更快失败或记为中断，而不是排队等待更久。

## 案例五：后台执行时，权限按什么判断

**问题**：提问先入队，再由后台线程领取执行。这时已经没有原来的 HTTP 请求和登录上下文，执行可能晚于提交，
也可能发生在另一个进程里。如果后台执行沿用提交时的身份而不复核，排队期间被停用的账号、被删除的助手、
被改过的配置都会照常执行；模型在工具参数里写一个没有授权的知识库 ID，也可能被直接检索。

**方案**：身份随任务落库，用的时候重新校验。

- 提交时把「谁提交的」和任务一起写入数据库：账号 ID、账号权限版本、登录会话摘要；游客则记录访客会话。
- 领取任务时重新校验身份与会话是否仍然有效、助手和模型是否可用；同时重新计算助手配置哈希（名称、提示词、
  模型、工具、知识库范围、对话参数），与提交时记录的不一致就拒绝执行，错误码 `AGENT_CONFIG_CHANGED`。
- 每次工具调用前再校验一次：知识库检索的 `kbsId` 参数必须在助手获准的知识库范围内，越界直接拒绝；
  公开体验的检索工具执行时还会再核对知识库是否在公开白名单里。

**验证结果**：端到端验收脚本用真实 HTTP 请求和真实模型运行，账号/管理员 40/40、游客 19/19 通过，
其中包括跨账号、跨访客访问被拒的检查；知识库参数越界被拒由单元测试覆盖。

**边界**：复核只针对执行时的身份与资源，不会撤回已经发出的模型请求；被拒绝的任务记为失败并给出错误分类，
不会换用别人的权限重试。

## 案例六：最终答复为什么要走专用通道

**问题**：Agent 循环的每一轮，模型都可能输出一段文字。模型在决定下一步时常写「我先检索一下」之类的决策旁白，
有的模型还会把推理过程写进正文；如果把这些内容直接推给用户，用户看到的是混着思考过程的文字。
另一个问题是「流程跑完」不等于「任务成功」：模型调用终止工具结束、或者既不调用工具也不给答复，
循环都会结束，但用户什么也没拿到。

**方案**：

- 把最终答复从模型正文里拆出来，设一个专用的「交付答复」工具（`directAnswer`）：模型必须调用它、
  把完整答复放进参数才算交付；中间轮的正文只作为内部过程，不当作答复推给用户。
- 以「是否通过答复通道交付」判定完成：循环即将结束但还没有交付答复时，系统注入一次提醒，让模型补一轮收尾；
  补过一次仍没有交付，就把这次运行记为失败（`NO_ANSWER_PRODUCED`），而不是显示为已完成。
- 循环本身有 20 步上限，防止模型反复调用工具而不收尾。

**边界**：答复通道只保证「交付的是模型明确写给用户的答复」，不保证答复内容正确；内容是否被来源支持，
由引用校验和人工阅读原文判断。

## 案例七：上一轮失败了，追问时会不会串题

**问题**：失败、取消或中断的运行只留下用户的提问，没有回答。下一轮把历史交给模型时，这条悬空的提问看起来
像「还没处理的任务」，模型可能把它和新问题一起回答；评测中出现过下一题的回答里顺带回答了上一题。
如果那一轮已经检索过，旧的检索结果留在上下文里，还可能被当作本轮的来源。

**方案**：按「轮」整理交给模型的历史，而不是按消息条数直接截断。

- 本轮完整保留；已经答完的历史轮整轮保留。
- 没答上的旧轮只保留用户提问，并插入一条说明：历史里未完成的问题只是上下文，不是本轮待办；
  那一轮的工具调用和检索结果全部丢弃，避免旧来源冒充本轮来源。
- 提示词同样约束：只回答当前这一条提问，用户明确追问上一轮时才沿用历史内容。

**验证结果**：单元测试覆盖失败轮、取消轮与正常轮混合时的历史投影结果。

**边界**：这是对输入的整理，不改变已保存的历史；用户明确要求重答上一题时，仍然可以回答。

## 从这七个案例能看出什么取舍

- 优先保证「不骗人」：宁可把一个运行记为中断或失败，也不写回一个无法证明归属的结果。
- 身份、配置和来源都在「用的时候」重新校验，而不是相信提交时的状态。
- 结论都带可复核的证据：数据库断言、真实 HTTP 请求、真实模型调用。
- 没有做的不装作做了：逐字流式输出、跨主机自动迁移、外部调用 exactly-once 都不在当前范围。
