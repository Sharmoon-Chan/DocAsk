## 问档 DocAsk 基于什么项目，继承了哪些能力

上游是 JChatMind：一个 Java + Spring Boot + Spring AI 的 AI Agent 示例项目，前端为 React，数据库为
PostgreSQL 加 pgvector 向量扩展。以下能力继承自上游，本仓库在其上维护与修正：

- Agent 主循环：Think–Execute 循环与状态机、步骤上限；关闭 Spring AI 内部工具执行，由循环自己执行工具并回填结果。
- 工具框架与「助手即数据」：工具声明与注册；助手的提示词、模型、工具、知识库范围存在数据表里，运行时按配置装配。
- 会话与消息持久化、SSE 状态推送、React 前端脚手架，以及 Dockerfile、Compose、Nginx 部署模板。
- 基础检索：Markdown 按章节解析，用章节标题生成向量，在 pgvector 中按 L2 距离取最近的 3 条。

源码依据：仓库 `docs/provenance.md` 的继承能力表，以及上游 `README.md`。

## 新增能力按两组概括

**第一组：让 Agent 在后台可靠地执行。** 对话执行从内存里的异步线程改为 PostgreSQL 持久化任务队列，文档导入也改为
入队后由后台处理：消息、输入快照和任务在同一个事务里写入，后台用一条 `FOR UPDATE SKIP LOCKED` 语句领取，
幂等键防止重复提交，租约心跳加 fencing token 拦截迟到的写入；重启后排队任务继续执行，运行中的任务记为中断而不重放。
后台执行时按提交时记录的身份重新校验权限和助手配置版本，每次工具调用前检查知识库范围。最终答复走专用的交付通道，
没交付答复就补一轮，仍然没有就记为失败。

**第二组：让回答可以被核对。** 检索从「标题向量」扩展为正文切块和版本化索引，每个片段带来源哈希、章节路径和
行号；答复里的引用只能指向本轮真实检索到的片段，编号对不上就整轮拒绝。每轮运行记录模型、检索、工具与落库的
耗时和状态。另外自建了 50 题冻结评测集，用来对比新旧索引并做失败归因。

支撑这两组能力的还有：账号与资源隔离、模型目录与密钥加密、游客体验入口和检查脚本，见下表。

## 引用编号是怎么和来源对应的

编号一律由**服务端**确定，不是检索排名，也不是文档行号。公开体验使用 `directAnswer` 交付通道：

- 模型调用 `directAnswer` 工具，正文写在 `answer` 参数里，用到的来源 id 按顺序放进 `citationIds` 数组。
- 正文里的 `[n]` 对应**本次答复 `citationIds` 数组的第 n 项**（从 1 开始）。模型只能从本轮检索命中里挑选来源，
  不能自己编造 id。
- 服务端逐个校验这些 id：是否是本轮真实检索返回的、是否仍在授权范围内；再去重、排序，并把正文编号同步改写为
  最终展示的编号。同一个来源在一次答复里只有一个编号。
- 正文里出现对不上 `citationIds` 的编号时，整轮判为无效（`INVALID_ANSWER_FORMAT`），不交付正文。

## 已实现但公开体验没有启用的结构化交付

- 第二条交付通道 `groundedAnswer`：模型逐条交付「一句陈述 + 一个来源 id + 该片段里的一段原文短引」，
  模型完全不写编号。服务端除了校验来源，还核对短引是否真的出现在该条来源自己的片段里，对不上就整轮无效；
  资料不足时走单独的「资料不足」结果，不挂任何引用。
- 这条通道由配置开关控制，默认关闭；公开体验目前使用上一节的 `directAnswer` 通道。
- 在隔离实例上用固定 30 题跑过：30 题运行全部成功，按事先写好的规则逐题核对原文行号，内容通过 29 题；
  3 道资料里没有答案的题都正确说明了资料不足。这是隔离实例的结果，不是公开体验的线上指标。

## 检索是怎么做的，效果怎么衡量

- 当前检索：问题用 BGE-M3 模型转成 1024 维向量，在知识库当前生效的索引版本里按 L2 距离取最近的 3 个正文片段。
  这是单路向量检索，没有关键词混合检索，也没有重排。
- 正文切块：按 Markdown 标题分段，段内按约 640 个估算 token、80 个重叠切块；新索引先建成候选版本，
  核对文档集合、来源哈希和向量模型后再原子切换，失败时旧版本保持不变。
- 评测：自建 50 题冻结评测集（40 题有答案、10 题资料不足，dev 30 题、test 20 题），指标 Hit@3、Recall@3、MRR@3。
  冻结判据下，上游的标题向量索引 Hit@3 为 0.850，正文切块为 0.600。
- 归因：44 个证据单元里有 17 个只差在标题行——判据把标题行算作证据位置，而正文片段不含标题行；
  真实的检索缺口只有 1 个。按正文窗口诊断，正文切块覆盖 43/44 个证据单元。
- 取舍：采用正文切块是为了让引用定位到行；冻结判据没有为了提高分数而修改，要改判据就重新冻结、两侧重跑。

## 哪些是「已实现」但不是「已验证」

- **多实例部署与网络分区**：代码按租约与 fencing 设计，只在单机双实例和真实进程终止下演练过，
  没有做过跨主机、时钟漂移、网络分区的验证。
- **远端 CI**：工作流文件已提交，是否真实执行过要看流水线记录，不能用本机结果代替。
- **多模型效果与成本对比**：没有做。

## 明确还没有做的

- **逐字流式输出**：答复由模型调用交付工具一次性给出，界面推送的是执行状态，没有正文的增量推送。
- **对外部调用的 exactly-once**：幂等只覆盖「同一会话的同一提交意图」，不覆盖模型或第三方服务。
- **混合检索、重排、检索阶段的拒答阈值**：都没有做。有答案和无答案问题的向量距离分布有重叠，单一阈值分不开。
- **PDF、Word 解析与自动模型降级**：没有做。
- **管理员跨用户读取**：这是刻意不做的隔离，不是缺陷。
- **跨模型的向量混用**：不同向量模型的向量不能混在一个索引里，换模型必须重新导入。

## 怎么核对这些说法

- 想看能力是否存在：对照 `docs/provenance.md` 和对应源码目录（如 `runs/`、`retrieval/`、`citation/`、`auth/`）。
- 想看是否验证过：看对应的测试文件与运行记录，注意区分单元测试、集成测试、真实浏览器和线上证据。
- 名称说明：产品对外名称是问档 DocAsk；仓库、数据库表前缀（`exobrain_*`）和部署目录沿用早期内部代号 `exobrain`，
  Java 包名沿用上游的 `com.kama.jchatmind`。
